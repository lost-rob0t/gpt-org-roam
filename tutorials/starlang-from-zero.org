* What StarLang is

StarLang is a small contract language and actor-runtime stack implemented in Common Lisp.

You use =.star= files to describe data and messages. The compiler turns those declarations into normalized contracts that the runtime can use for documents, actors, manifests, dispatch, and adapters.

The important part is that StarLang is *Lisp-shaped, but it is not Common Lisp source*.

#+begin_example
.star source
    |
    v
parser -> expansion -> validation -> compiler
    |
    v
normalized contracts
    |
    +-> documents
    +-> actor/runtime manifests
    +-> runtime dispatch
#+end_example

If you want the deeper architecture after this tutorial, read [[id:dca7bf46-7062-4e34-bfaf-8bec6e520a42][StarLang Compiler and Runtime Architecture]].

* Run it

Clone the repo and enter the Nix shell:

#+begin_src sh
git clone https://github.com/lost-rob0t/star-lang
cd star-lang
nix develop
#+end_src

Run the test suite before changing anything:

#+begin_src sh
nix run .#tests
nix flake check -L
#+end_src

You can also load the current implementation directly in SBCL:

#+begin_src lisp
(require :asdf)
(asdf:load-system :starlang-prototype)
#+end_src

The repository is still moving code out of =prototype/= into final =star-*= and =starlang-*= systems. Treat package locations as less permanent than the architectural boundaries.

* Your first StarLang file

Create =hello.star=:

#+begin_src lisp
(spec-library "org.example/hello@1"
  (:version "1.0.0")

  (document greeting
    (:persistence persistent)
    (text string :required)))
#+end_src

That says:

- this library is =org.example/hello@1=;
- its version is =1.0.0=;
- it defines one persistent document called =greeting=;
- =greeting= has one required string field called =text=.

Nothing in that file is evaluated as Common Lisp.

Load it from the REPL:

#+begin_src lisp
(defparameter *hello*
  (star-lang.api:load-star-file #P"hello.star"))
#+end_src

That is the normal high-level path.

* The compiler pipeline

When something breaks, use the individual compiler phases instead of staring at =load-star= and hoping enlightenment arrives.

#+begin_src lisp
(defparameter *source*
  "(spec-library \"org.example/hello@1\"
      (:version \"1.0.0\")
      (document greeting
        (:persistence persistent)
        (text string :required)))")

(defparameter *syntax*
  (star-lang.api:read-star-syntax *source*))

(defparameter *expanded*
  (star-lang.api:expand-star-syntax *syntax*))

(star-lang.api:validate-star-core *expanded*)

(defparameter *ir*
  (star-lang.api:compile-star-core *expanded*))
#+end_src

The phases are:

#+begin_example
read-star-syntax
    -> parse source and preserve source locations
expand-star-syntax
    -> expand bounded StarLang macros
validate-star-core
    -> reject invalid language constructs
compile-star-core
    -> produce normalized runtime-neutral IR
#+end_example

This is also your debugging map. Parse failure and runtime failure are not the same species of problem, despite computers' heroic attempts to make them feel identical.

* Types

StarLang lets you build domain types instead of passing anonymous strings and integers everywhere.

**Scalar**

#+begin_src lisp
(scalar task-id
  (:base string
   :pattern "^[a-z0-9-]{3,64}$"))
#+end_src

**Enum**

#+begin_src lisp
(enum task-status
  (queued running completed failed))
#+end_src

Use an enum when the accepted values really are closed. Use a string when outside systems may legitimately invent new values.

**Lists and maps**

Current contracts use types such as:

#+begin_example
string
integer
decimal
boolean
symbol
map
reference
iso-date
iso-datetime
(list string)
#+end_example

See [[id:c91d5283-f96e-4d95-92f6-a926ea6951f5][StarLang Spec Libraries and Portable Contracts]] for more detail.

* Documents and messages

A document describes stored or transient data:

#+begin_src lisp
(document task
  (:persistence persistent)
  (taskId task-id :required)
  (description string :required)
  (status task-status :required))
#+end_src

A message describes actor/runtime communication:

#+begin_src lisp
(message run-task
  (:fields
   ((taskId task-id :required))))
#+end_src

Do not treat messages and documents as interchangeable just because they contain similar fields.

A command may ask an actor to change state. The resulting stored document is a different contract.

* A small real library

Put this in =tasks.star=:

#+begin_src lisp
(spec-library "org.example/tasks@1"
  (:version "1.0.0")

  (scalar task-id
    (:base string
     :pattern "^[a-z0-9-]{3,64}$"))

  (enum task-status
    (queued running completed failed))

  (document task
    (:persistence persistent)
    (taskId task-id :required)
    (description string :required)
    (status task-status :required))

  (message run-task
    (:fields
     ((taskId task-id :required))))

  (message task-completed
    (:fields
     ((taskId task-id :required)
      (summary string :required)))))
#+end_src

Load it:

#+begin_src lisp
(defparameter *tasks*
  (star-lang.api:load-star-file #P"tasks.star"))
#+end_src

Now you have a domain contract with persistent data and an actor protocol.

* Creating documents

The runtime can construct documents from a compiled graph:

#+begin_src lisp
(defparameter *task*
  (star-lang.api:create-document
   *tasks*
   "task"
   '(("taskId" . "task-001")
     ("description" . "Learn StarLang")
     ("status" . queued))
   :dataset "tutorial"))
#+end_src

Notice the field spelling: =taskId= stays lower camelCase.

That is deliberate. Wire, document, manifest, and serialized field names preserve their StarLang spelling instead of quietly mutating into Lisp naming conventions.

Encode a document:

#+begin_src lisp
(defparameter *encoded*
  (star-lang.api:encode-document
   *task*
   :key-style :camel
   :couchdb t))
#+end_src

Decode it again:

#+begin_src lisp
(defparameter *decoded*
  (star-lang.api:decode-document
   *tasks*
   "task"
   *encoded*))
#+end_src

* IDs and relations

Documents can use generated or deterministic ID policies. The runtime currently supports ULIDs, UUIDv4, and digest-based IDs.

Digest IDs are useful when the same logical object should always receive the same ID from the same canonical fields.

Relations are documents too. The runtime exposes:

#+begin_src lisp
(star-lang.api:relate-documents
 graph
 source-document
 destination-document
 :predicate "member-of")
#+end_src

When changing relation schemas, keep compatibility at a clear boundary. Normalize old input once and write canonical output. Supporting three spellings forever in every layer is how software becomes folklore.

* Imports

Libraries can import other libraries:

#+begin_src lisp
(import "org.starintel/core@1"
  :version "1.0.0"
  :digest "sha256:...")
#+end_src

The important idea is reproducibility: imports are exact contract dependencies, not fuzzy package discovery.

For real code, inspect the loader and current fixtures before inventing new import behavior.

* Actors

StarLang's runtime is actor-oriented. The useful mental model is:

#+begin_example
message
  |
  v
runtime directory
  |
  v
deterministic dispatcher
  |
  v
actor mailbox / handler
  |
  +-> journal
  +-> lease
  +-> capability checks
  +-> adapter ports
#+end_example

These parts are separate on purpose.

- The *directory* resolves logical actor/service identity.
- The *dispatcher* routes a command deterministically.
- The *mailbox* protects single-actor message processing semantics.
- The *journal* records durable state needed for recovery/replay.
- A *lease* represents time-bound ownership.
- An *adapter* performs external side effects such as HTTP or process execution.

A network connection being alive does not magically solve all six problems. Humans tried that architecture already.

* Service URIs

StarLang supports logical service identities shaped like:

#+begin_example
star://domain:address:actor-name
#+end_example

For example:

#+begin_example
star://bbp:localhost:nmap
#+end_example

This names the service independently from the transport used to reach it.

That distinction matters. A StarLang contract should describe the logical actor/service. It should not become coupled to “RabbitMQ queue X” or “HTTP URL Y” unless the contract is specifically about that adapter.

The parser/runtime APIs for service URIs live behind the actor-protocol boundary, with compatibility wrappers still present in the transitional implementation.

* Runtime-neutral IR

This is the architecture rule worth tattooing on the inside of your debugger:

#+begin_quote
Normalized StarLang IR describes semantics, not concrete runtime calls.
#+end_quote

Bad idea:

#+begin_example
(:operation :cl-gserver-cast ...)
#+end_example

Better idea:

#+begin_example
actor/message/service contract
#+end_example

Then the runtime maps that contract onto Sento, RabbitMQ, HTTP, a process adapter, or whatever transport is appropriate.

Generated Python or TypeScript bindings consume portable contracts. They are not alternate StarLang implementations.

* How to debug StarLang

When a change fails, find the layer first.

| Symptom | Start here |
|-
| Source will not parse | =read-star-syntax= |
| Macro-generated declaration is wrong | =expand-star-syntax= |
| Invalid contract is accepted/rejected | =validate-star-core= |
| Manifest/IR is wrong | =compile-star-core= |
| Import cannot resolve | loader/import graph |
| Document IDs/fields are wrong | document runtime |
| Message reaches wrong actor | directory + dispatcher |
| Duplicate side effect | idempotency + journal + adapter |
| Remote actor appears alive but fails | directory, lease, transport separately |

When adding a language feature, test it in roughly this order:

1. parser;
2. validation;
3. normalized IR;
4. real =.star= fixture;
5. runtime behavior, if applicable;
6. full ASDF/Nix suite.

Tests are especially important in a language implementation because the model you have in your head is usually the thing being tested, not just the code you typed.

* Mini project: BBP tool runner

The repo contains a real BBP fixture. Before reading it, try building a smaller version yourself.

Define:

#+begin_src lisp
(enum tool-name
  (subfinder httpx katana nmap))

(enum tool-run-status
  (queued running completed failed cancelled))
#+end_src

Then add a persistent =tool-run= document with:

#+begin_example
runId
programId
tool
target
argv
status
exitCode
stdout
stderr
#+end_example

Add two messages:

#+begin_example
run-tool
tool-run-completed
#+end_example

Load the library, construct a =tool-run= document, encode it, and deliberately try invalid values.

Then compare your design to:

#+begin_example
fixtures/bbp-domain.star
#+end_example

Finally trace how a command aimed at:

#+begin_example
star://bbp:localhost:nmap
#+end_example

would move through the runtime directory, dispatcher, actor, and process adapter.

If you can explain why the service URI belongs in the logical contract but the process invocation belongs behind an adapter, you have the core architecture.

* Done when

You are ready to work on StarLang when you can:

- write and load a small =spec-library=;
- explain parser -> expansion -> validation -> compiler;
- define scalars, enums, documents, and messages;
- construct and encode a document;
- explain why field spelling and deterministic IDs matter;
- trace a message through directory -> dispatcher -> actor;
- distinguish journal, lease, transport, and adapter responsibilities;
- explain why normalized IR cannot contain raw Sento/CL-GServer operations;
- run the real test suite before and after a change.
