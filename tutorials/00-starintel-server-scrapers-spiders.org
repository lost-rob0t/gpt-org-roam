You will build two projects:

* 2. The architecture you are about to build

The final data path is:

#+begin_example
                 PROJECT B
          +----------------------+
          |   Scrapy spider      |
          |                      |
seed ---> | GET page             |
          | parse HTML           |
          | follow links         |
          | normalize document   |
          +----------+-----------+
                     |
                     | AMQP publish
                     | exchange: documents
                     | key: documents.ingest.url
                     v
              +-------------+
              |  RabbitMQ   |
              +------+------+ 
                     |
                     | documents.ingest.#
                     v
                 PROJECT A
          +----------------------+
          |   starintel-server   |
          |                      |
          | ingest consumer      |
          | normalize _id        |
          | write CouchDB        |
          | attach _rev          |
          +----------+-----------+
                     |
                     +----> CouchDB / Clouseau
                     |
                     | publish documents.new.url
                     v
          downstream actors / observers
#+end_example

The distinction between =documents.ingest.url= and =documents.new.url= matters.

=documents.ingest.url= means:

#+begin_quote
Please persist this new =url= document.
#+end_quote

=documents.new.url= means:

#+begin_quote
This =url= document is already durable and has been emitted as a post-insert
event.
#+end_quote

Publishing a brand-new finding directly to =documents.new.url= bypasses normal
ingest persistence.

* 3. What is a scraper?

A scraper extracts structured values from one fetched representation.

Given:

#+begin_src html
<article>
  <h1>Example title</h1>
  <p class="body">Example body.</p>
</article>
#+end_src

a scraper might produce:

#+begin_src json
{
  "title": "Example title",
  "body": "Example body."
}
#+end_src

The important verbs are:

#+begin_example
fetch -> parse -> select -> normalize
#+end_example

A scraper does not have to discover additional URLs.

* 4. What is a crawler?

A crawler discovers additional resources and schedules them.

Given:

#+begin_src html
<a href="/article-a.html">A</a>
<a href="/article-b.html">B</a>
#+end_src

a crawler adds those links to a frontier and fetches them later.

The important verbs become:

#+begin_example
fetch
  -> parse
  -> extract data
  -> discover links
  -> normalize links
  -> deduplicate links
  -> schedule more requests
#+end_example

* 5. What is a spider?

In frameworks such as Scrapy, "spider" normally means the component that owns
crawl behavior:

- seed URLs;
- which responses to parse;
- which links to follow;
- which items to emit;
- spider-specific limits and policy.

A useful mental model is:

#+begin_example
scraper = page -> data
crawler = pages -> more pages
spider  = crawler policy + parsing callbacks
#+end_example

A real spider contains scraper logic, but a scraper does not necessarily crawl.

* 6. The crawl frontier

A crawl frontier is the set of work that has been discovered but not yet fully
processed.

Conceptually:

#+begin_example
seen = {canonical URLs already scheduled}

frontier = [
  URL waiting for fetch,
  URL waiting for fetch,
  ...
]
#+end_example

A production crawler also tracks:

- priority;
- retry count;
- domain;
- next eligible request time;
- source page;
- crawl depth;
- content type;
- last fetch time;
- robots policy;
- tenant/dataset;
- trace identity.

Scrapy already gives you a scheduler, request deduplication, downloader,
middleware, retry machinery, and concurrency controls. That is why Project B
will graduate from a tiny hand-written scraper into Scrapy instead of
reimplementing a crawler runtime accidentally.

* 7. Scraping is not permission to hammer a site

This tutorial uses a local fixture site first.

When adapting the spider to a real site:

- obey applicable law and authorization;
- respect =robots.txt= unless you have a legitimate reason and authorization not
  to;
- identify your user agent where appropriate;
- use finite concurrency;
- use delays;
- honor explicit rate limits;
- do not bypass authentication or access controls;
- do not add CAPTCHA bypass or anti-bot evasion to a general crawler;
- minimize collection of sensitive personal data;
- retain provenance so a collected fact can be audited;
- prefer official APIs when they are the more stable and authorized interface.

A fast crawler that gets your IP blocked is not a good crawler.

* 23. The exact RabbitMQ topology

The current StarIntel messaging documentation defines a durable topic exchange:

#+begin_example
exchange: documents
type:     topic
#+end_example

Important flows:

| Flow | Queue | Topic |
|------+-------+-------|
| persist new document | =documents.ingest= | consumer binds =documents.ingest.#= |
| emit new typed document | — | producer uses =documents.ingest.<dtype>= |
| post-insert event | actor-specific | =documents.new.<dtype>= |
| update ingest | =documents.updates.ingest= | =documents.updated.#= |
| persisted target intake | =documents.targets= | =documents.new.target.#= |
| remote actor target | actor-specific | =actors.<actor>.new.target= |

For our page documents:

#+begin_example
documents.ingest.url
#+end_example

is the producer key.

* 24. What StarIntel does after our publish

When Project B publishes a JSON body to:

#+begin_example
documents / documents.ingest.url
#+end_example

the current server:

1. parses the JSON;
2. requires a non-empty =dtype=;
3. generates =_id= if absent;
4. writes the document to CouchDB;
5. adds the returned =_id= and =_rev=;
6. publishes the enriched document to =documents.new.url=;
7. ACKs the ingest delivery after the required work succeeds.

That last ordering is why downstream actors should consume
=documents.new.url= when they require a persisted document.

* 25. Delivery is at least once

StarIntel explicitly documents at-least-once processing.

A failure can happen after an external side effect and before an ACK.

Therefore:

#+begin_example
delivery once       -> possible
delivery twice      -> possible
delivery many times -> possible
exactly once        -> NOT guaranteed
#+end_example

Our spider must be idempotent.

We will accomplish that by giving deterministic page snapshots deterministic
IDs.

* 26. Why deterministic IDs are useful for spiders

Suppose a page is fetched twice and produces identical normalized content.

If both attempts use random IDs:

#+begin_example
crawl 1 -> url-A
crawl 2 -> url-B
#+end_example

you created a duplicate.

If both use a stable digest:

#+begin_example
id = SHA256(canonical URL + normalized content)
#+end_example

then:

#+begin_example
crawl 1 -> url-8c...
crawl 2 -> url-8c...
#+end_example

CouchDB's conflict becomes a natural duplicate signal.

If page content changes, the content hash changes and the tutorial producer
creates a new snapshot.

That is a useful immutable-snapshot model for scraping.

#+begin_src python
from __future__ import annotations

import hashlib
import re
import time
from urllib.parse import parse_qsl, urlencode, urlsplit, urlunsplit


_WHITESPACE = re.compile(r"\s+")


def normalize_text(value: str) -> str:
    return _WHITESPACE.sub(" ", value).strip()


def canonical_url(value: str) -> str:
    parts = urlsplit(value)

    scheme = parts.scheme.lower()
    host = (parts.hostname or "").lower()

    if not scheme or not host:
        raise ValueError(f"absolute URL required: {value!r}")

    port = parts.port
    if port is None:
        netloc = host
    elif (scheme == "http" and port == 80) or (
        scheme == "https" and port == 443
    ):
        netloc = host
    else:
        netloc = f"{host}:{port}"

    path = parts.path or "/"

    # Stable order for ordinary query pairs.
    query = urlencode(sorted(parse_qsl(parts.query, keep_blank_values=True)))

    # Fragments are client-side location identifiers and are intentionally
    # omitted from the crawl identity here.
    return urlunsplit((scheme, netloc, path, query, ""))


def content_sha256(content: str) -> str:
    digest = hashlib.sha256(content.encode("utf-8")).hexdigest()
    return f"sha256:{digest}"


def snapshot_id(url: str, content: str) -> str:
    canonical = canonical_url(url)
    normalized = normalize_text(content)

    payload = (
        "starintel-url-snapshot-v1"
        + "\0"
        + canonical
        + "\0"
        + normalized
    ).encode("utf-8")

    return "url-" + hashlib.sha256(payload).hexdigest()


def make_url_document(
    *,
    url: str,
    title: str,
    text: str,
    dataset: str,
    spider: str,
    http_status: int,
    source_url: str | None = None,
    parent_id: str | None = None,
) -> dict:
    canonical = canonical_url(url)
    split = urlsplit(canonical)
    content = normalize_text(" ".join(part for part in [title, text] if part))
    now = int(time.time())

    document = {
        "_id": snapshot_id(canonical, content),
        "dataset": dataset,
        "dtype": "url",
        "sources": [spider, source_url or canonical],
        "version": "0.8.0",
        "dateAdded": now,
        "dateUpdated": now,
        "url": canonical,
        "path": split.path,
        "query": split.query,
        "content": content,
        "extensions": {
            "scraper": {
                "spider": spider,
                "http_status": http_status,
                "content_sha256": content_sha256(content),
            }
        },
    }

    if parent_id:
        document["extensions"]["star_server"] = {
            "parent_id": parent_id,
        }

    return document
#+end_src

* 39. Why canonicalize URLs?

These can refer to the same logical resource:

#+begin_example
HTTP://EXAMPLE.COM:80/a#section
http://example.com/a
#+end_example

Without canonicalization, a crawler may schedule and store equivalent URLs as
different resources.

Our tutorial canonicalizer:

- lowercases scheme;
- lowercases host;
- removes default ports;
- ensures a path exists;
- sorts ordinary query pairs;
- drops fragments.

This is intentionally conservative.

Do not blindly sort query parameters for every production site. Some
applications treat parameter order as meaningful.

* 40. Why normalize text?

HTML-derived text often contains:

- line breaks;
- tabs;
- repeated spaces;
- layout whitespace.

If a deterministic ID hashes unnormalized text, harmless formatting changes can
create new snapshots.

We normalize runs of whitespace to one space before hashing.

For evidence-grade archival crawling, keep the raw response separately too.
Normalized text is a projection, not a replacement for raw evidence.

* 41. Why hash content and URL?

If identity used only the URL:

#+begin_example
same URL + new content -> same ID
#+end_example

Then a new crawl would need the update path.

For this tutorial we prefer immutable page snapshots:

#+begin_example
same URL + same content -> same ID
same URL + new content  -> new ID
#+end_example

This also makes duplicate Rabbit delivery naturally idempotent.

A production system may choose a stable resource ID plus versioned snapshot
documents instead. The important thing is to define the model deliberately.

* 45. Why declare the exchange?

Project A creates/uses:

#+begin_example
documents / topic / durable
#+end_example

Project B declares the same topology defensively.

RabbitMQ will reject incompatible redeclarations instead of silently turning a
topic exchange into a different kind of exchange.

* 46. Why publisher confirms?

A normal =basic_publish= call can tell you that your process handed bytes to a
client library. Publisher confirms let the broker acknowledge the publish.

That still does not mean:

#+begin_quote
The document is safely stored in CouchDB.
#+end_quote

It means the Rabbit publish reached the broker under the confirm contract.

The later =documents.new.url= event is the better signal that StarIntel finished
the insert path.

* 47. Why delivery_mode=2?

AMQP delivery mode =2= marks the message persistent.

For durable queueing you need the topology and message behavior to agree:

#+begin_example
durable exchange
+ durable queue
+ persistent message
+ RabbitMQ persistence behavior
#+end_example

Even then, durability is a broker guarantee, not an exactly-once application
guarantee.

* 55. Why this does not loop forever

The fixture graph contains a cycle.

Scrapy's request fingerprinter/scheduler filters duplicate requests by default.

So the sequence is effectively:

#+begin_example
schedule index
schedule A
schedule B
see index again
duplicate request fingerprint -> filtered
#+end_example

We also set =DEPTH_LIMIT= as a second termination control.

Do not confuse URL dedupe with business-document idempotency. They solve
different duplicate classes.

* 56. Page extraction choices

Our first spider extracts all body text:

#+begin_src python

#+begin_src python
from __future__ import annotations

import json
import os

import pika
from pika.exceptions import AMQPConnectionError, UnroutableError

from star_spider.starintel import make_url_document


class RabbitMQPublisherPipeline:
    def __init__(self):
        self.connection = None
        self.channel = None

    def open_spider(self, spider):
        self._connect()

    def close_spider(self, spider):
        if self.connection and self.connection.is_open:
            self.connection.close()

    def _connect(self):
        credentials = pika.PlainCredentials(
            os.environ["STAR_RABBIT_USER"],
            os.environ["STAR_RABBIT_PASSWORD"],
        )

        self.connection = pika.BlockingConnection(
            pika.ConnectionParameters(
                host=os.environ.get(
                    "STAR_RABBIT_HOST",
                    "127.0.0.1",
                ),
                port=int(
                    os.environ.get(
                        "STAR_RABBIT_PORT",
                        "5672",
                    )
                ),
                virtual_host="/",
                credentials=credentials,
                heartbeat=30,
                blocked_connection_timeout=30,
                connection_attempts=3,
                retry_delay=2,
            )
        )

        self.channel = self.connection.channel()

        self.channel.exchange_declare(
            exchange="documents",
            exchange_type="topic",
            durable=True,
        )

        self.channel.confirm_delivery()

    def process_item(self, item, spider):
        document = make_url_document(
            url=item["url"],
            title=item.get("title", ""),
            text=item.get("text", ""),
            dataset=item.get("dataset", "default"),
            spider=item.get("spider", spider.name),
            http_status=int(item.get("http_status", 0)),
            source_url=item.get("source_url"),
            parent_id=item.get("parent_id"),
        )

        self._publish(document)

        return item

    def _publish(self, document):
        if not self.connection or self.connection.is_closed:
            self._connect()

        dtype = document["dtype"]
        routing_key = f"documents.ingest.{dtype}"

        body = json.dumps(
            document,
            separators=(",", ":"),
            ensure_ascii=False,
        ).encode("utf-8")

        try:
            self.channel.basic_publish(
                exchange="documents",
                routing_key=routing_key,
                body=body,
                mandatory=True,
                properties=pika.BasicProperties(
                    content_type="application/json",
                    content_encoding="utf-8",
                    delivery_mode=2,
                    type=dtype,
                    app_id="starintel-web-spider",
                ),
            )
        except (AMQPConnectionError, UnroutableError):
            # Fail the crawl item instead of pretending it was stored.
            raise
#+end_src

* PART VI — RELATIONS: TURN A CRAWL INTO A GRAPH

* 64. A crawler naturally discovers edges

If page A links to page B, that is not merely a crawling implementation detail.

It can be a graph fact:

#+begin_example
A --links-to--> B
#+end_example

StarIntel already has =links-to= in its relation predicate vocabulary.

So a spider can emit both:

- URL documents;
- relation documents.

* 65. Separate resource identity from snapshot identity

For a large system, consider two concepts:

#+begin_example
resource
  canonical URL identity

snapshot
  canonical URL + observed content identity
#+end_example

This tutorial currently stores snapshot-like =url= documents.

When you need stable link relations despite changing content, introduce a
stable resource identity or map canonical URLs to current snapshots.

Do not hide this modeling problem inside a hash function.

* 66. Build relation documents

A simple tutorial relation shape can be:

#+begin_src python
import hashlib
import time


def relation_id(source_id: str, target_id: str, predicate: str) -> str:
    payload = "\0".join(
        [
            "starintel-relation-v1",
            source_id,
            predicate,
            target_id,
        ]
    ).encode("utf-8")

    return "relation-" + hashlib.sha256(payload).hexdigest()


def make_relation(
    *,
    dataset: str,
    source_id: str,
    target_id: str,
    predicate: str,
    note: str,
) -> dict:
    now = int(time.time())

    return {
        "_id": relation_id(
            source_id,
            target_id,
            predicate,
        ),
        "dataset": dataset,
        "dtype": "relation",
        "sources": ["tutorial_site"],
        "version": "0.8.0",
        "dateAdded": now,
        "dateUpdated": now,
        "source": source_id,
        "target": target_id,
        "predicate": predicate,
        "note": note,
    }
#+end_src

Use =links-to= for hyperlink edges.

Publish relations through:

#+begin_example
documents.ingest.relation
#+end_example

not =documents.new.relation=.

* 67. Why relations must also be idempotent

The page may be crawled repeatedly.

If every observation generates a random relation ID, you can create thousands
of duplicate =links-to= edges.

A deterministic relation ID from:

#+begin_example
source + predicate + target
#+end_example

makes repeated observation safe.

If you need a historical observation log, model observation events separately
instead of turning duplicate graph edges into a timestamp journal.

* 68. Provenance is part of scraping correctness

A scraped fact without provenance is hard to audit.

At minimum preserve:

- canonical source URL;
- spider name;
- collection time;
- content hash;
- HTTP status;
- dataset;
- source/parent identity if this crawl came from a StarIntel target.

For recursive actor networks, the server documentation recommends propagating
metadata such as:

#+begin_example
trace_id
root_id
parent_id
actor_path
depth
hop
max_depth
max_hops
#+end_example

The server does not automatically add those fields for you.

* 69. Do not put secrets in provenance

Never include:

- RabbitMQ password;
- CouchDB password;
- Authorization header;
- session cookie;
- bearer token;
- proxy credential;

inside the document, =sources=, =extensions=, logs, or actor events.

Operational provenance and authentication material are different categories.

* PART VII — HTTP BEHAVIOR OF A REAL SPIDER

* 70. Timeouts are mandatory

A spider without timeouts can accumulate hung requests until the crawl is
effectively dead.

Scrapy has downloader timeouts. Set a finite value:

#+begin_src python
DOWNLOAD_TIMEOUT = 20
#+end_src

Tune it to the target class.

Do not set "infinite because some sites are slow."

* 71. Retry only retryable failures

Typical retry candidates include transient:

- connection resets;
- some DNS/network errors;
- 429;
- 500;
- 502;
- 503;
- 504.

Do not repeatedly retry a permanent parsing error or an authorization denial.

Every retry consumes:

- time;
- bandwidth;
- server load;
- crawl budget.

* 72. Backoff

Scrapy's default retry behavior is not a complete politeness strategy.

For high-value production crawls, track attempt timing and use bounded
exponential backoff:

#+begin_example
1s
2s
4s
8s
stop
#+end_example

Add jitter when many workers could retry together.

* 73. Handle 429 explicitly

=429 Too Many Requests= means your current request rate is not accepted.

Respect =Retry-After= when present.

Also lower concurrency rather than simply sleeping one request while the rest of
the worker pool keeps hammering the same host.

* 74. robots.txt

We set:

#+begin_src python
ROBOTSTXT_OBEY = True
#+end_src

That is the right default for a general tutorial spider.

A =robots.txt= decision is not the same as legal authorization, but ignoring it
by accident is poor crawler hygiene.

* 75. Per-domain concurrency

We set:

#+begin_src python
CONCURRENT_REQUESTS_PER_DOMAIN = 2
#+end_src

This prevents global concurrency from becoming per-site concurrency.

When scaling to many domains, this lets the crawler remain productive without
concentrating all requests on one origin.

* 76. Download delay

We set:

#+begin_src python
DOWNLOAD_DELAY = 0.25
RANDOMIZE_DOWNLOAD_DELAY = True
#+end_src

For real sites, 250 ms may still be too aggressive.

Start conservative and tune from observed responses and stated policies.

* 77. User agent

A crawler should not pretend to be Chrome merely because it can.

Use an identifiable agent:

#+begin_example
starintel-web-spider/0.1
#+end_example

For a public service you control, include an operator/contact URL or email if
appropriate.

* 78. Content types

Do not parse every response as HTML.

A production spider should inspect =Content-Type= and route:

#+begin_example
text/html        -> HTML parser
application/json -> JSON handler
application/pdf  -> PDF pipeline
image/*          -> media pipeline
other            -> metadata only / skip
#+end_example

A crawler is a dispatcher over representation types, not just a CSS selector
engine.

* 79. Response-size ceilings

A malicious or accidental huge response can exhaust memory.

Set maximum response/download sizes appropriate to the job.

Large files should go through a streaming/archive path instead of being loaded
into one giant string and stored directly inside a StarIntel document.

* 80. HTML is hostile input

Even when you are not executing JavaScript, HTML can be pathological:

- malformed nesting;
- huge attribute values;
- millions of nodes;
- deceptive encodings;
- compressed bombs;
- repeated boilerplate.

Treat parser and response limits as part of the security boundary.

* 81. JavaScript-rendered pages

Scrapy fetches HTTP responses. It does not magically execute every JavaScript
application.

Before adding a browser:

1. inspect network/API calls;
2. see whether useful data is in initial HTML;
3. see whether a documented API exists;
4. see whether embedded JSON is enough.

Browser automation is heavier, less deterministic, and easier to abuse.

Do not make Playwright your default HTTP client.

* 87. Minimal target daemon

A simple learning daemon can consume one target at a time and launch the Scrapy
job.

Create =target_daemon.py=:

#+begin_src python
from __future__ import annotations

import json
import os
import subprocess
import sys

import pika


QUEUE = "actors.web-spider.targets"
BINDING = "actors.web-spider.new.target"


def connection():
    credentials = pika.PlainCredentials(
        os.environ["STAR_RABBIT_USER"],
        os.environ["STAR_RABBIT_PASSWORD"],
    )

    return pika.BlockingConnection(
        pika.ConnectionParameters(
            host=os.environ.get(
                "STAR_RABBIT_HOST",
                "127.0.0.1",
            ),
            port=int(
                os.environ.get(
                    "STAR_RABBIT_PORT",
                    "5672",
                )
            ),
            virtual_host="/",
            credentials=credentials,
            heartbeat=30,
        )
    )


conn = connection()
channel = conn.channel()

channel.exchange_declare(
    exchange="documents",
    exchange_type="topic",
    durable=True,
)

channel.queue_declare(
    queue=QUEUE,
    durable=True,
)

channel.queue_bind(
    queue=QUEUE,
    exchange="documents",
    routing_key=BINDING,
)

channel.basic_qos(prefetch_count=1)


def on_target(ch, method, properties, body):
    target = json.loads(body)

    if target.get("dtype") != "target":
        ch.basic_nack(
            method.delivery_tag,
            requeue=False,
        )
        return

    url = target.get("target")
    dataset = target.get("dataset", "default")
    parent_id = target.get("_id", "")

    if not isinstance(url, str) or not url.startswith(
        ("http://", "https://")
    ):
        ch.basic_nack(
            method.delivery_tag,
            requeue=False,
        )
        return

    command = [
        sys.executable,
        "-m",
        "scrapy",
        "crawl",
        "tutorial_site",
        "-a",
        f"start_url={url}",
        "-a",
        f"dataset={dataset}",
        "-a",
        f"parent_id={parent_id}",
    ]

    completed = subprocess.run(
        command,
        check=False,
    )

    if completed.returncode == 0:
        ch.basic_ack(method.delivery_tag)
    else:
        ch.basic_nack(
            method.delivery_tag,
            requeue=True,
        )


channel.basic_consume(
    queue=QUEUE,
    on_message_callback=on_target,
    auto_ack=False,
)

print(f"waiting on {QUEUE} / {BINDING}")

try:
    channel.start_consuming()
finally:
    conn.close()
#+end_src

* 88. Why the tutorial daemon launches a subprocess

This implementation is intentionally easy to understand.

It creates one clean Scrapy process per target.

Tradeoffs:

- simple lifecycle;
- strong isolation between jobs;
- expensive process startup;
- only one target at a time with =prefetch_count=1=;
- not ideal for high-throughput crawling.

A production service can run a long-lived job supervisor using Scrapy's
=CrawlerRunner= or another worker architecture.

Learn the message contract first. Optimize the process model second.

* 89. ACK only after the crawl succeeds

The target daemon uses:

#+begin_example
crawl return code == 0 -> ACK
crawl failure          -> NACK / requeue
#+end_example

ACKing immediately when the target is received would mean:

#+begin_quote
Rabbit thinks the job is complete even if the spider crashes one second later.
#+end_quote

That is an easy way to lose work.

* 90. But requeue forever is also wrong

This tutorial daemon requeues failures for clarity.

Production must classify failures.

Examples:

**Permanent**

- invalid URL;
- unsupported scheme;
- explicitly denied target;
- malformed target;
- site removed and policy says do not retry.

**Transient**

- temporary Rabbit outage;
- DNS outage;
- 503;
- transient network reset.

Permanent failures should not bounce forever.

Use:

- dead-letter exchange;
- bounded retry count;
- retry queues with delay;
- terminal actor event.

The current core server does not create your external actor DLQ for you.

* 93. Recurring targets

A target can set:

A zero-delay recursive loop can turn the system into a message amplifier.

* PART IX — RELIABILITY AND MESSAGE SEMANTICS

* 95. At-least-once across two layers

Project B has at least two retry domains:

#+begin_example
HTTP retry domain
Rabbit delivery retry domain
#+end_example

They are not the same.

A page can be fetched twice due to HTTP retry logic.

A resulting document can be delivered twice due to Rabbit processing.

Deterministic identity should tolerate both.

* 96. Publisher failure before confirm

Possible sequence:

#+begin_example
Project B sends bytes
connection fails
Project B does not know whether broker accepted them
#+end_example

This is an outcome-uncertain window.

Retrying may duplicate the publish.

That is why the document itself must be idempotent.

Do not make network transport uncertainty disappear by pretending it cannot
happen.

* 97. Consumer crash after side effect

Possible Project A sequence:

#+begin_example
receive document
write CouchDB
crash before ACK
Rabbit re-delivers
#+end_example

Again, deterministic identity prevents a second logical insert.

Exactly-once behavior is an application property built from idempotency and
state, not a magical Rabbit switch.

* 98. Prefetch

A consumer prefetch controls how many unacknowledged deliveries can be in
flight.

Our target daemon sets:

#+begin_src python
channel.basic_qos(prefetch_count=1)
#+end_src

That is deliberately conservative because each target launches a whole crawl.

A lightweight transformation worker could use a larger prefetch.

* 99. Backpressure

Suppose spiders produce faster than StarIntel can persist.

RabbitMQ becomes the buffer.

But a buffer is finite in reality.

Watch:

- queue depth;
- message bytes;
- consumer rate;
- publish rate;
- CouchDB write latency;
- disk free space.

"Rabbit is buffering it" is not a capacity plan.

* 100. Rabbit connection reuse

Do not open a new AMQP TCP connection for every scraped item.

Our pipeline opens one connection in =open_spider= and closes it in
=close_spider=.

That is far cheaper than:

#+begin_example
page
-> TCP connect
-> AMQP handshake
-> auth
-> channel
-> one message
-> close
#+end_example

for every page.

* 101. Connection recovery

The tutorial pipeline reconnects if it notices a closed connection before a
publish.

A stronger production publisher also handles:

- mid-publish connection loss;
- channel closure;
- broker restart;
- heartbeat timeout;
- bounded reconnect backoff;
- confirm uncertainty;
- graceful drain on shutdown.

Keep that code in the transport layer.

* 102. Message size

Do not send multi-megabyte raw websites through RabbitMQ merely because AMQP can
carry bytes.

A scalable design often uses:

#+begin_example
object store / archive -> raw body
StarIntel document     -> metadata + extracted content + archive reference
RabbitMQ               -> bounded work/event envelope
#+end_example

RabbitMQ is a broker, not your blob store.

* 103. Transient work

The server recognizes =transient: true= and filters it out of standard ingest
and update consumers.

Use transient messages for intermediate work that should not enter CouchDB.

Do not use =transient= for evidence that must be reproducible.

* 104. Updates

The current server update path consumes the =documents.updated.#= topic family.

Use an update when you are changing an existing durable identity rather than
creating a new snapshot.

The server:

- requires =_id= and =dtype=;
- refetches current state;
- deep-merges the patch;
- uses the latest =_rev=;
- retries conflicts;
- emits the updated revision.

For our immutable page snapshot tutorial, new content creates a new document, so
we do not need updates yet.

* PART X — RECURSION AND LOOP CONTROL

* 105. Crawlers are recursive systems

A spider is recursion expressed as dataflow:

#+begin_example
page
  -> discovered link
     -> page
        -> discovered link
           -> page
              ...
#+end_example

StarIntel actors are also recursive dataflow.

Combining them means you have recursion at two levels:

#+begin_example
crawler recursion
+ actor graph recursion
#+end_example

That deserves explicit budgets.

* 106. Crawl depth

Scrapy:

#+begin_src python
DEPTH_LIMIT = 8
#+end_src

This bounds hyperlink traversal depth.

StarIntel actor metadata may have its own:

#+begin_example
depth
max_depth
hop
max_hops
#+end_example

Do not reuse Rabbit delivery count as either one.

* 107. Actor path

If one StarIntel actor launches another, maintain:

#+begin_example
actor_path = [
  "seed",
  "web-spider",
  "content-classifier"
]
#+end_example

A non-repeatable actor should not invoke itself indefinitely.

Crawler link cycles and actor cycles are separate checks.

* 108. Fixed points

A page normalization pipeline can stop producing a new derived document when:

#+begin_example
normalized output hash == previous output hash
#+end_example

This is a fixed point.

Fixed-point thinking is useful for recursive enrichment systems:

#+begin_example
input
-> enrichment
-> enrichment
-> no semantic change
-> stop
#+end_example

* 109. Crawl budgets

Add explicit job limits:

#+begin_example
max pages
max bytes downloaded
max depth
max wall time
max errors
max retries
max domains
#+end_example

A crawl that has no termination budget is not production-ready.

* 114. Test layers

* 116. Spider parse test

You can test a callback with a local response object.

Example:

#+begin_src python
from scrapy.http import HtmlResponse, Request

from star_spider.spiders.tutorial_site import TutorialSiteSpider


def test_parse_emits_item_and_links():
    html = b"""
    <html>
      <head><title>A</title></head>
      <body>
        <article><p>Hello</p></article>
        <a href="/b.html">B</a>
      </body>
    </html>
    """

    request = Request(
        "http://127.0.0.1:8008/a.html"
    )

    response = HtmlResponse(
        request=request,
        url=request.url,
        body=html,
        encoding="utf-8",
    )

    spider = TutorialSiteSpider()
    output = list(spider.parse(response))

    items = [
        value
        for value in output
        if not isinstance(value, Request)
    ]

    requests = [
        value
        for value in output
        if isinstance(value, Request)
    ]

    assert len(items) == 1
    assert items[0]["title"] == "A"

    assert len(requests) == 1
    assert requests[0].url.endswith("/b.html")
#+end_src

No RabbitMQ required.

For a transport test:

1. start RabbitMQ;
2. create a temporary queue bound to =documents.ingest.url=;

4. consume one message;

#+begin_example

- whether publish fails visibly;
- whether reconnect is bounded;
- whether uncertain publishes remain idempotent.

For Project B:

1. crawl once;
2. restart Project A;
3. wait for health;
4. crawl again;

* PART XIII — DEBUGGING PLAYBOOK

* 121. Spider gets connection refused on port 8008

Check:

#+begin_src sh
curl http://127.0.0.1:8008/index.html
#+end_src

If that fails, RabbitMQ is irrelevant.

Fix the fixture HTTP server.

* 122. Spider parses no links

Inspect:

#+begin_src python

#+end_src

Then inspect the actual response body.

Do not change Rabbit routing because a CSS selector returned nothing.

* 123. Rabbit authentication fails

#+end_src

#+begin_src sh
wc -c ~/Projects/starintel-server/secrets/rabbitmq_password
#+end_src

* 124. Rabbit publish is unroutable

#+begin_example

#+end_example

* 125. Queue grows forever

Possible causes:

- star-server unhealthy;
- CouchDB unavailable;
- ingest consumer repeatedly NACKing;
- malformed document;
- too few workers;
- publisher rate exceeds durable write rate.

Inspect Project A logs before scaling Project B harder.

* 126. Document never appears in CouchDB

Check:

1. was publish confirmed?
2. did message route to =documents.ingest=?
3. did =dtype= exist?
4. did star-server log parse/insert errors?
5. did CouchDB return conflict or bad request?
6. is the document =transient:true=?

Trace one ID through each layer.

* 127. Document is in CouchDB but observer sees nothing

Make sure observer bound to:

#+begin_example
documents.new.url
#+end_example

not:

#+begin_example
documents.ingest.url
#+end_example

Also ensure the observer was running before the event unless its queue is
durable and retained.

Our tutorial observer uses an exclusive temporary queue, so it sees only live
events.

* 128. Search does not show new document

Check CouchDB first.

If the document exists there, wait for indexing and inspect Clouseau/search.

Persistence success and full-text visibility are not the same event.

* 129. Duplicate documents appear

Ask:

- is =_id= deterministic?
- is content normalized before hashing?
- is URL canonicalized?
- does a timestamp participate in the ID?
- does nondeterministic field ordering participate in the hash?
- are redirects producing multiple canonical URLs?

Never put =time.time()= into deterministic identity input.

* 130. Crawl loops

Inspect:

- canonical URL function;
- query parameter explosion;
- =DEPTH_LIMIT=;
- Scrapy duplicate-filter stats;
- calendar/search/faceted navigation traps.

A site can generate infinitely many unique URLs even when request deduplication
is working perfectly.

* 131. Crawl is too slow

Measure before changing concurrency.

Possible bottlenecks:

#+begin_example
remote HTTP
HTML parsing
item pipeline
Rabbit confirm latency
StarIntel/CouchDB ingest
local CPU
DNS
#+end_example

If Rabbit publish confirms are the bottleneck, increasing HTTP concurrency may
only make memory/backpressure worse.

* 132. Crawl is too fast for the target

Lower:

#+begin_example
CONCURRENT_REQUESTS_PER_DOMAIN
DOWNLOAD_DELAY
#+end_example

Honor 429/Retry-After.

A high scrape rate is not automatically a performance win.

* PART XIV — HARDEN PROJECT B

* 133. Validate items before publish

Before transport, require:

#+begin_example

finite content size
known extension shape
deterministic ID
#+end_example

Fail locally.

Do not send obviously malformed documents merely to see whether Project A
accepts them.

* 134. Bound content length

For example:

#+begin_src python
MAX_CONTENT_CHARS = 200_000

content = normalize_text(content)

if len(content) > MAX_CONTENT_CHARS:
    content = content[:MAX_CONTENT_CHARS]
#+end_src

Better systems preserve truncation metadata:

#+begin_src json
{
  "truncated": true,
  "original_chars": 481233,
  "stored_chars": 200000
}
#+end_src

Silent truncation destroys auditability.

* 135. Preserve raw hashes

Even if raw HTML is stored elsewhere, record:

#+begin_example
raw_body_sha256
normalized_text_sha256
#+end_example

Then you can distinguish:

- response changed;
- normalization changed;
- extraction changed.

* 136. Archive raw pages separately

A mature architecture:

#+begin_example
HTTP response
   |
   +--> immutable raw archive / object storage
   |
   +--> normalized StarIntel url document
           |
           +--> archive URI
           +--> body hash
           +--> parser version
#+end_example

This makes parsers re-runnable without re-contacting the source site.

* 137. Version the parser

Add:

#+begin_src json
{
  "extensions": {
    "scraper": {
      "parser": "tutorial-html",
      "parser_version": "1"
    }
  }
}
#+end_src

When extraction logic changes, provenance can explain why two normalizations
differ.

* 138. Domain allowlists

A target-driven spider must not blindly crawl any URL a message can inject if
the deployment intends a restricted scope.

Validate against an explicit allowlist:

#+begin_example
allowed schemes
allowed domains
allowed ports
blocked private networks when appropriate
#+end_example

Server-side request forgery risks apply to crawlers too.

* 139. IP and hostname policy

If targets can be untrusted, consider blocking:

- loopback;
- link-local;
- cloud metadata endpoints;
- internal management networks;

unless the crawler is explicitly an internal-network collector authorized to
reach them.

The local fixture is loopback because this is a controlled tutorial.

Do not copy that policy unchanged into a public multi-user service.

* 140. Redirect policy

A permitted starting URL can redirect to a forbidden destination.

Validate redirect destinations against the same network/domain policy.

Scope applies after redirects too.

* 141. Credentials and authenticated crawling

If a crawler must use credentials:

- isolate them per target/site;
- never persist them in normal StarIntel page documents;
- redact request/response headers from logs;
- make cookie jars scoped;
- encrypt secrets at rest;
- define who is authorized to launch that crawl.

Do not turn a general target document into a plaintext password envelope.

* PART XV — SCALING

* 142. First scaling strategy: more Project B workers

Rabbit external actors are natural horizontal services.

Instead of one process doing everything:

#+begin_example
actors.web-spider.targets
  -> worker 1
  -> worker 2
  -> worker 3
#+end_example

Use competing consumers on the same queue for target-level parallelism.

Each crawl still enforces per-domain politeness.

* 143. Do not multiply per-domain load accidentally

If you run ten workers and each allows two requests per domain, the actual
aggregate can become twenty concurrent requests to one domain.

Global service-level rate limiting must account for all workers.

Per-process settings are not a distributed rate limiter.

* 144. Partition by domain when necessary

At larger scale, consider routing or scheduling targets by canonical host:

#+begin_example
example.org -> worker partition A
example.net -> worker partition B
#+end_example

This makes distributed politeness and caches easier to reason about.

* 145. Separate target queue from page frontier

RabbitMQ is excellent for coarse jobs:

#+begin_example
crawl this site / target
#+end_example

Scrapy's scheduler is better for a spider's internal page frontier.

Do not put every single discovered hyperlink into the global StarIntel target
queue unless you actually need cross-process global scheduling.

Use the right queue at the right granularity.

* 146. Separate CPU-heavy parsing

If extraction becomes CPU-heavy:

#+begin_example
fetch worker
-> raw artifact
-> parser worker
-> StarIntel documents
#+end_example

Do not block HTTP download concurrency on an expensive NLP transform if the
tasks can be decoupled.

* 147. Batch versus single-message ingest

Single-document Rabbit messages are simple and observable.

Batching can improve throughput but complicates:

- retry granularity;
- partial failure;
- idempotency;
- max message size;
- traceability.

Start with one document per message.

Measure before batching.

* PART XVI — STRICT 0.9 MIGRATION

* 148. Why this tutorial did not invent a strict 0.9 url object

The server's documentation explicitly warns that the current Rabbit ingest path
does not call the strict 0.9 validator.

The exact canonical 0.9 schema should come from the StarIntel conformance/spec
repository, not from our memory.

Therefore the tutorial's runnable bridge uses fields that the current server
documents exactly.

That is more honest than writing a "0.9" object that merely looks plausible.

* 149. Migration plan

When moving Project B to strict 0.9:

1. pin the canonical 0.9 schema;
2. generate/use the official language adapter if available;
3. choose the canonical =dtype=;
4. validate locally before publish;
5. preserve extensions under the allowed extension boundary;
6. add conformance fixtures;
7. test Rabbit round-trip preservation;
8. test CouchDB round-trip preservation;
9. verify downstream actors understand the nested =data= shape;
10. only then switch the active producer.

* 150. Do not silently normalize dtype aliases

Strict 0.9 rejects legacy aliases rather than silently converting them.

That is good.

A distributed system should not have three producers disagreeing about the
canonical type while one server guesses what they meant.

Normalize explicitly at a versioned compatibility boundary.

* PART XXI — DESIGN QUESTIONS

* 170. Should RabbitMQ carry every discovered link?

Usually no.

Use the Scrapy frontier for page-level crawling unless a link must become global
distributed work.

Rabbit targets are better for coarse durable jobs.

* 171. Should the spider write CouchDB directly?

For this architecture, no.

That would bypass:

- StarIntel ingest routing;
- post-insert events;
- a single document-flow boundary;
- future validation/enforcement;
- actor subscriptions.

Project B should publish to RabbitMQ and let Project A own persistence.

* 172. Should the spider call the StarIntel HTTP API instead?

It can be a useful boundary for some clients.

But the user goal in this tutorial is explicitly to learn the RabbitMQ actor
path.

Use RabbitMQ when building an external actor/service intended to participate in
distributed StarIntel messaging.

* 173. Should RabbitMQ be exposed publicly?

No by default.

The Compose configuration binds it to loopback for a reason.

For remote actors:

- private network;
- VPN/tunnel;
- least-privilege Rabbit user/vhost;
- explicit TLS support;
- firewall;
- credential rotation.

The current StarIntel Rabbit client documentation warns that merely switching
to port 5671 does not prove verified TLS has been configured.

* 174. Why not use auto_ack?

Because receipt is not completion.

If Project B receives a target, auto-ACKs it, then crashes during crawl, the
broker cannot redeliver the target.

Manual ACK lets the actor define completion.

* 175. Why not ACK after the first page?

Because the target represents a crawl job.

Define the target's success condition.

For this tutorial it is:

#+begin_quote
The Scrapy job process exits successfully after its required publishes.
#+end_quote

A production actor can use finer job/checkpoint semantics.

* 176. Why not make each page a target?

You can, but that turns the global actor system into the crawl frontier.

That may be useful for:

- distributed page ownership;
- global dedup;
- long-lived crawl scheduling.

It also adds:

- huge Rabbit traffic;
- more persistence;
- more actor recursion;
- more difficult politeness.

Choose it intentionally.

* PART XXII — GLOSSARY

* 177. Scraper

Code that extracts structured data from fetched content.

* 178. Crawler

A system that discovers and schedules more resources while traversing a graph of
links.

* 179. Spider

A crawler policy/component, especially in Scrapy, that defines seeds, parsing,
and link-following behavior.

* 180. Crawl frontier

Discovered work not yet fully processed.

* 181. Canonical URL

A normalized representation used to reason about URL identity.

* 182. Idempotent

Safe to repeat without creating unintended duplicate logical effects.

* 183. Exchange

RabbitMQ routing entity that receives publishes and routes them to queues.

* 184. Topic exchange

An exchange that matches routing keys against dot-separated binding patterns.

StarIntel's =documents= exchange is a topic exchange.

* 185. Queue

RabbitMQ storage/delivery endpoint consumed by workers.

* 186. Routing key

The topic string attached to a publish.

Examples:

#+begin_example
documents.ingest.url
documents.new.url
actors.web-spider.new.target
#+end_example

* 187. ACK

Consumer acknowledgement that a Rabbit delivery completed successfully.

* 188. NACK

Negative acknowledgement. It may requeue or reject/dead-letter depending on
configuration.

* 189. Publisher confirm

Broker acknowledgement of a publish.

It is not the same as application-level persistence in CouchDB.

* 190. CouchDB revision

The =_rev= value attached by CouchDB to a stored document revision.

* 191. Snapshot

An immutable observation of a resource at a point/version of content.

* 192. Provenance

Metadata and relations describing where a document came from and how it was
derived.
